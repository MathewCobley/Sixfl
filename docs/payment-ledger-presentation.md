# Payment ledger presentation contract

The canonical financial ledger remains authoritative. Presentation must not alter receipts, obligations, allowances, original fixture fees, credit, or collection decisions to make a display balance.

`getPlayerPaymentDisplay` exposes two deliberately distinct amounts:
- `amountPence`: the existing player-facing obligation/receipt presentation, retained for player-account and repayment semantics.
- `fixtureContributionPence`: verified received money plus an explicitly recognised SIXFL adjustment. Pending liabilities and money held by the captain do not count as SIXFL player receipts. Remittances appear through their existing accounting route.

Team Payments uses the second amount for every bold player contribution and totals the displayed rows. The same canonical cash and adjustment split is shown by the shared `getPlayerSettlementBreakdown` helper in Team Payments and Squad Payments (headline, cards, fixture selector). Missing historical cap evidence remains a review state; an £8 allocation and £5 receipt alone never create a £3 allowance. An unexplained difference between linked rows and the ledger is shown, not fabricated away.

Squad Payments retains the stored captain allocation via `hydrateCaptainAssignedPlayerFees` and `getCaptainAssignedPlayerFeePence`, independently of the lower real player receipt. It uses the canonical settlement split, not a separate page-local cap boost. A recoverable team waiver can settle the team balance while player links remain open; the native summary continues to explain that later payments reduce the waiver before creating credit.

`getChargeDescriptionForDisplay` removes only the exact old autogenerated coverage sentence from rendered descriptions. The stored description and accounting/audit markers remain unchanged. Current settlement text uses the canonical entry, including waivers and excess recorded settlement, not that historical sentence. Excess settlement is not automatically described as cash or team credit.

The obsolete captain-page rewriting in `apply-team-charge-waiver-accounting.cjs` and `apply-player-match-fee-cap.cjs` is retired to source assertions. The cap script's page-only meta-rewrites are removed from `apply-modern-payment-script-compatibility.cjs`; its administrative-policy patches remain intact. The native settled summary takes precedence over the old summary rewrite in `apply-waiver-payment-ui-consistency.cjs`, preserving the recoverable-waiver contract. Accounting, admin cap controls, checkout/webhook/credit logic and other legacy preparation are unchanged. Native page markup owns the presentation; no new permanent source-rewriting patch or DOM bridge is introduced.

## Verification

The anonymised five-player regression must display 800 + 800 + 800 + 800 + 500 = 3700 pence, separated into 1800 received and 1900 adjustments. Partial receipts, refunds, captain-held money, waivers, excess, mismatched rows and admin-only correction visibility are covered.

The workflow runs these tests before and after full prebuild, critical feature/DOM contracts, TypeScript and the production build. Negative controls restore the mixed-column and stale-description bugs and must fail. Browser tests use actual rendered page markup and production CSS at 1440, 1280 and 390 pixels, with external requests blocked. The existing real PostgreSQL player-ledger workflow retains refund, duplicate webhook, partial payment, allowance and credit coverage. Final source search inventory and prepared-page diffs are saved with the browser screenshots.

Production deployment/startup must be verified separately from tests. No live customer test payments or historic record repairs are necessary for this presentation fix.
