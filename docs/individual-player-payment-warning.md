# Individual player payment warning

Admin Payments → Open player fees due → **Send payment warning** beside the selected fee. The original **Chase player** button is unchanged. A separate admin page resolves that exact saved fee, displays the player/fixture/amount, and offers one selected permitted channel (email or SMS), a UK-local deadline, preview, explicit acknowledgement and confirmation. A preview alone is read-only and never creates a recipient, payment link or queue entry. Email HTML uses the existing sandboxed preview component. SMS preview displays the real payment destination, explaining shortening on queueing.

`src/lib/payments/player-payment-warning.ts` is the shared preview/confirmation/provider authority; policy and signed-preview verification live beside it. Both server actions require an administrator. A signed 15-minute preview binds the admin, fee, deadline, channel and exact recipient/content snapshot. Changed data requires a new preview. Confirmation locks the fee and uses a unique request ID so double clicks and network retries cannot produce duplicate warnings. One pending warning at a time and 24 hours between sent warnings for the same fee. Old normal reminder stages do not exhaust this separate manual warning.

Only a positive OPEN player fee with a linked, named player and existing canonical payment token/link for a published, non-cancelled match can be warned. Paid/waived/cancelled and captain-collected records are blocked. Missing or stale contact/linkage is held for review, not silently repaired. Existing opt-outs and suppression are preserved and checked across matching recipient records. The message uses the actual individual fee amount, not a captain's nominal share. It does not change balances, collect money, create links, set an account-wide deadline, add late fees, remove a player or impose a suspension. Existing payment checkout safeguards still apply.

The selected deadline is at least one hour from the permitted sending time and within 30 days. UK daylight saving changes are validated; non-existent or ambiguous local deadlines are rejected. SMS respects the existing 09:00–21:00 UK window, including delayed queue processing. Both providers recheck current fee state, contact/preferences, content and deadline immediately before submission. A paid or obsolete queued warning is cancelled. Unexpected delivery errors remain in the existing queue for review, never automatically re-created. The source is `PLAYER_MATCH_FEE_WARNING`, with admin, fee, deadline and request ID recorded in dispatch metadata/history.

Two editable transactional PLAYER templates are installed idempotently, preserving edits and disabled settings. Templates must retain the payment URL and deadline; the default wording is firm but makes no threat of an unauthorised charge or suspension. Template changes after preview/queueing require a fresh confirmation. Delivery is via the existing notification queue; no new scheduled job is introduced.

Verification: dedicated disposable PostgreSQL/provider-stub tests cover read-only preview, explicit admin authorization, token tampering/expiry, real queue concurrency, exact individual scope, consent, fee/link/contact changes, both provider gates, SMS hours, failures and migration idempotency. Real React controls are exercised in Chromium at desktop/mobile sizes. Tests run after full production source preparation with existing critical-feature checks and build; no production player or real email/SMS is used.
