# Announcement queue feedback

Admin → Comms → Announcements now uses the native `AnnouncementSendPanel` and the authenticated `/api/admin/announcements` endpoint. The first click immediately disables submission and shows **Queueing announcement…**. The request creates queue rows only; it never waits for Resend or runs the notification processor. The existing notifications cron delivers queued messages normally. No cron configuration is changed.

The panel refreshes persisted counts while queueing or delivery is outstanding, distinguishing **Queued**, **Sending**, **Sent to provider**, **Failed — review**, **Skipped** and **Cancelled**. Sent to provider is not a claim of inbox delivery or readership. **Check progress** is read-only, and **View this announcement in Queue** opens the existing queue filtered to this exact template revision. Counts include historical rows, so the mailing already sent before this change remains visible and is not started again.

If the HTTP response is lost or times out, the form says the result is unconfirmed and does not automatically retry. The administrator must check progress before explicitly queueing only addresses without a recorded outcome. A recipient-level PostgreSQL transaction/advisory lock makes the persisted check and queue insertion atomic across duplicate clicks or separate tabs. Failed, skipped, cancelled, processing and sent records are not automatically recreated by this button. An immutable email snapshot is preferred over a recipient's subsequently edited address; older rows without that snapshot still use the existing recipient linkage.

Both the saved template revision and normalized audience are fingerprinted at review time. A changed template or contact list must be reviewed again before a new submission. Queueing uses a bounded four-worker database loop and snapshots that reviewed content/audience for the request. A partial failure leaves already committed queue rows intact and reports that remaining addresses need checking. The UI tells the administrator to keep the page open until queueing is confirmed; after confirmation they can leave while delivery continues through the existing sender. No unsupported background promises or detached request tasks are used.

The prior server action is retained as a compatibility boundary, now using the same protected queue-only service; stale old forms without a reviewed fingerprint cannot send. `queueDirectNotification` gains an optional transaction client, like the existing template queue path, while default callers retain their existing behaviour. This allows both queued and skipped dispatch writes to commit or roll back with the duplicate check. Native page, preview, referral destination, italics, suppression and existing permission classification are otherwise unchanged.

No database migration, production customer send, campaign re-run, manual queue/cron run or recipient/marketing-permission change is part of deployment. The temporary branch-only editing workflow is removed from the final tree. Automated tests use synthetic contacts and a localhost PostgreSQL database, actual queue code/SQL and real Chromium controls with an isolated HTTP boundary. Production rollout and authenticated live use are reported separately in the pull request.
